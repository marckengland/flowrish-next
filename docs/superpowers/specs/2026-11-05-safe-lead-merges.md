# Safe lead merges

User-approved scope: side-by-side preview, explicit confirmation, fresh permission/version checks, linked-data preservation or blocking, transactional audit. Mocks/synthetic data only; no new dependencies, DeepSeek calls, emails, widget activation, or real business-data verification writes. Session authorizes integration and deployment after verification. Existing property-test updates and six added browser scenarios (76→82) approved.

Keep the chosen primary lead's scalar fields, stage, owner, score and lifecycle state. Merge two active, accessible leads within one workspace. Require leads:read, leads:write and leads:delete. Archive secondary with deletedAt and mergedIntoId; retain all scalar values. Transfer its activities, tasks, stage transitions and score history; copy missing contact links without deleting original archive links. Block secondary leads with any cadence enrollments, follow-up suggestions, receptionist calls, callback/waitlist CRM handoffs or prior merged children. These workflows need a separate lifecycle migration. Nothing sends or executes as a consequence of confirmation.

A private organization-owned, actor-scoped LeadMergeReview holds immutable primary/secondary IDs, snapshot hash, expiry, and applied receipt. Ten-minute previews; max20 pending per actor/workspace, actor-scoped expired-pending cleanup. Applied receipts/manifests remain with business audit history and survive staff offboarding; current membership is still required for every operation. Server computes the complete lead snapshot and bounded related ID/hash sets. Review includes both records' fields, differences, linked counts and blockers; blocked reviews cannot be confirmed. Cap500 combined source/destination linked rows to bound work; larger merges require separate support.

Apply locks membership, review, both leads in sorted order, then related rows; refreshes authorization after waits; rechecks expiry and the full snapshot. All transfers, conditional archive/primary timestamp writes, audit and receipt are one transaction. Replays use the same review ID and never repeat writes. Mutation endpoints enforce same-origin bounded JSON and expected workspace/user fences. Legacy one-click endpoint rejects unreviewed requests; destructive legacy implementation is removed.

A database mergedIntoId marker, same-workspace target check, and link guards on all current leadId tables prevent an in-flight writer from attaching new work to an archived merge source after a lock wait. Guards apply only to merged sources; ordinary deleted leads keep their existing behavior. Archived merged rows reject edits until explicit operator restoration. Future schema additions with leadId must install the guard too.

UI direction can choose either record to keep before preview. Changing candidate/direction clears unconfirmed review. Confirmation requires a checkbox. Uncertain apply retains the same ID with explicit retry and blocks new merges; no automatic retries. Fresh success navigates to retained lead. Read-only users can search permitted matches, but only delete-authorized users can merge.

Recovery: prepare an independently tested code switch disabling merge writes while keeping table/marker/guards and history. Operator-only data undo restores only an unchanged archived source and unchanged retained lead, returns exact transferred IDs with post-merge fingerprints, removes only copied contact links, and preserves later/unrelated edits by refusing the entire repair. No production repair is executed. Blocked workflow-linked merges, field-by-field value selection, bulk merges, automatic merging and undo UI remain deferred.
