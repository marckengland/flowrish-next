# Email attention notifications

User accepted: add owner-scoped in-app alerts for pending email replies and unresolved address matches, direct review links, waiting age, deduplication and stale-alert removal. Reuse current UI, no dependencies/providers/DeepSeek/emails/widget activation. Sending remains explicit. Baseline main024948858af8acc2bbf6bbcc01d2092783cfcfb2; protected existing isolated checkout, preserve unrelated.serena and original.spec-workflow.

Use a query-derived inbox with durable per-member read receipts. EmailNotificationRead stores only organizationId/userId/key/readAt, unique by those IDs; FK to current membership cascades offboarding, RLS enabled and browser grants revoked. No router/sync changes, sweep, backfill, source edits or alert duplication. Existing pending work appears immediately; edits do not create fresh notification keys. Resolved/inaccessible/reassigned/disconnected work disappears on the next read. Mark read only acknowledges the personal alert.

Eligibility is shared by count/list/read/target: current membership and lead-read permission; own mailbox in the workspace; stored routing owner/provider/email binding. Match alerts require PENDING routing. Reply alerts require ROUTED source, exact mailbox-scoped suggestion source identity, PENDING owned EMAIL suggestion, same live activity/lead and current lead visibility. Source keys hash kind+message+suggestion identity; no subject/body/lead name is copied into alerts. Readonly users can acknowledge their own alert but cannot approve work.

New /api/email-notifications list/count/[key] endpoints use expected-user/workspace equality fences, no-store/private responses, bounded same-origin JSON for acknowledgments and safe errors. Counts/lists never write. Read receipts serialize by actor/key, reread permission/source after waits, and return the first timestamp on repeated acknowledgments. Invalid or stale source/access rejects with no new receipt. API target read supports focused pending follow-up records without the normal100-item cap, with current source/lead access checks. No task creation from target retrieval.

Production header/Notifications page pass current org/user context into existing UI via optional props; old callback behavior/API/fixtures stay intact. Bell aggregates callback+email counts with one polling cycle, no hidden-tab requests, no stale-context response reuse; failure is distinguishable from zero. Email inbox section has own unread/all pagination and refresh/read actions. Failure/revocation clears stale rows. Stable local links target the specific match preview or follow-up card; resolved targets display an unavailable notice rather than stale data. Target reads never auto-generate, approve, send, or discard another open draft. Fresh notification events refresh counts after review; periodic refresh removes stale alerts.
