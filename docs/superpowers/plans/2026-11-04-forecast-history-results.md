# Forecast history and monthly results

Goal: record the basis of new forecasts, identify unverified legacy data, and compare personal monthly commitments with won revenue using matching owner, USD, and UTC periods. Use existing Prisma, services, components, and isolated browser rehearsal. No new dependencies, provider calls, email, real leads, widget changes, historical backfills, or production verification writes.

## Decisions

- Add nullable currency, reporting timezone, calculation version, and scope to ForecastSubmission and ForecastSnapshot with one additive migration and no defaults. Legacy rows stay unverified. New submissions describe the submitter's assigned deals; scheduled snapshots describe the whole business. This is standard versioned-reporting metadata.
- Show six UTC calendar months of personal results, newest first. Query actual won revenue with explicit organization, assignee, USD, closed-won state, and inclusive start/exclusive end. Use exact Decimal arithmetic for differences and percentages. Actuals reflect current CRM state and can change after reassignment, reopening, or edits; the current month is in progress. These are not immutable accounting statements.
- Only compare supported metadata with the expected scope. Unknown or incompatible commits receive no risk, variance, or attainment. Do not silently reuse them as verified form defaults. Keep business snapshots separate from owner commitments and hide monetary values whose basis is unknown or unsupported.
- Apply the same compatibility and owner scope to the forecast page, comparison API, and dashboard comparison. Keep business headline totals unchanged. Add a read-only history API with session, permission, and entitlement checks; URL parameters cannot select another owner or organization.
- Reuse existing cards and table styles for monthly results and snapshot history, with explicit status text, loading/error/empty states, and local horizontal scrolling on small screens. Add isolated desktop/mobile browser coverage without changing existing test assertions.
- Work inline on `codex/forecast-history-results` in the clean existing checkout, preserving unrelated untracked directories. Obtain one fresh whole-change review before integration. Existing session instructions authorize finish/merge/push; production DDL must use the reviewed additive migration, never db push. No production data backfill or test records.

This approach makes organization-local calendar reports, FX conversion, and immutable sales attribution harder later: each needs its own recorded basis or event history. Do not claim older currency or historical ownership can be recovered from current rows.
