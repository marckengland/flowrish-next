# Mocked receptionist browser rehearsal

Run `npm run test:receptionist:mocked` from the repository root. Install the existing browser dependency first if needed: `npx playwright install chromium`.

The command builds this separate fixture application and runs the 112 browser scenarios. It imports the real client components, uses synthetic read data, and runs without authentication or production credentials. It does not import the production middleware, server modules, database, or auth client.

Workspace scenarios use a synthetic `mock_workspace` cookie only in this fixture app. They exercise the real selector and fetch boundary, full document reloads, stale-context recovery, and notifications to other tabs. The fixture cookie never selects a production organization. Server unit tests separately exercise real middleware/session membership and OAuth boundaries with mocked identities and providers.

The runner removes inherited credentials and URLs. Server sockets can reach only its selected loopback ports; private environment files cannot be read (the checked-in `.env.example` template is permitted). Chromium uses a proxy that permits fixture reads and blocks every other destination or unmocked mutation. Negative probes verify these guards before the workflows run. Any guard violation fails the command even if the UI swallows the error. Results are under the ignored `test-results/rehearsal/` directory.

There is no auth setup, saved browser session, retry, or production base URL. All 112 scenarios must pass without skips. Update the explicit selection and count together when adding coverage. CI runs this command alongside the unit suite; migrations wait for both checks. CI generates the project's Prisma types with dummy URLs and makes no database connection.

This fixture checks client workflows. Production authentication and database transactions remain separate coverage. The normal Flowrish app gains no test login mode or fixture routes. Production receptionist/widget settings are never changed.

Eight pipeline and forecast scenarios cover desktop drag-and-drop, mobile stage selection, won/lost outcomes, reopening, rejected and uncertain saves, pending controls, empty lists, read-only access, and denied reads. The forecast references are hand-calculated from synthetic USD and PHP deals. Server regressions separately verify record permissions, conditional stage updates, transactional conversion, current-user commits, and entitlement checks. Database rollback and locking are modeled with mocks; this rehearsal does not verify a live Postgres transaction.

Four forecast-history scenarios add desktop/mobile monthly results, legacy and incompatible basis labels, zero commitments, denied-read recovery, held loading, and empty snapshot history. Every request carries the synthetic workspace header; mutations, providers, emails, and widget requests remain forbidden.

Current forecast money values and submissions use USD without currency conversion. Win rate counts deals in every currency. Reporting months use UTC consistently on the server and in the browser. New commitments record owner scope; daily snapshots record business scope. Stored currency, timezone, and calculation version determine compatibility. Older rows with missing metadata remain unverified. Personal monthly actuals reflect current CRM ownership and won status, so reassignment, reopening, and edits can change them. Historical snapshots are never backfilled by this feature.

Core workflow fixtures import the production dashboard panels, lead/task forms and lists, and follow-up inbox. The compiler replaces only the three exact lead, task, and forecast action imports with client-only fake adapters; every other production server module and credential client remains forbidden. Unmocked form writes are blocked by the read-only proxy. The extra action-boundary probe verifies those exact substitutions and rejects relative production imports.

Eight keyboard-audit scenarios exercise real dialogs, lead/task forms, mobile navigation and native business switching on desktop/mobile Chromium. Only the exact browser Supabase-client import is replaced by a local function that throws if invoked; real auth clients, server modules and database imports remain forbidden. A ninth safety probe verifies this boundary. The fixture reuses the checked-in logo via a symlink. Additional cases cover editable-note focus and mobile-to-desktop resizing. Native date values are prepared as test data; screen-reader speech output and other engines are outside this rehearsal.

Six personal follow-up snooze scenarios cover tomorrow/custom local time, mobile layout, explicit wake, callback reminder links, revision-specific read receipts, draft-discard consent, uncertain saves and stale/read-only access. All original 106 scenarios and network/write guards remain. Separate disposable PostgreSQL checks verify actual transaction rollback, due filtering, current ownership, mailbox proof and private schema constraints.
